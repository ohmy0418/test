너는 개발자가 Jira 요구사항 변경을 안전하게 반영하도록 돕는 개발 어시스턴트야.
대상 이슈: $ARGUMENTS

**중요 원칙: 요구사항이 변경된 것을 발견하더라도 코드를 임의로 수정하지 마. 분석 결과를 먼저 보여주고, 개발자가 명시적으로 진행을 승인한 뒤에만 구현을 시작해.**

> 이 명령은 `/jira-start`가 남긴 스냅샷을 기준선으로 사용한다. 키 처리·스냅샷 경로·스키마·브랜치명 규칙은 반드시 `jira-start.md`와 동일하게 유지해야 두 명령이 같은 파일을 읽고 쓴다. 한쪽 규칙을 바꾸면 다른 쪽도 함께 바꿔야 한다.

## 1단계: 입력값 검증  (jira-start와 동일하게 처리)
- `$ARGUMENTS`가 비어 있으면 중단하고, 이슈 키를 입력하라고 안내해줘.
- 이슈 키 형식은 아직 확정되지 않았으니 특정 형식을 강제하지 않는다. 입력받은 값을 그대로 이슈 키로 사용한다.
  - 다만 공백으로 여러 값이 들어오면(예: `GAF-11 급함`) 어느 것이 이슈 키인지 모호하므로, 임의로 추측하지 말고 중단해서 사용자에게 확인해줘.
- 앞뒤 공백만 제거하고, 값 자체는 사용자가 입력한 그대로 사용한다.
  - **주의**: 이 키가 곧 스냅샷 파일명(`<KEY>.md`)이 된다. `jira-start`와 조금이라도 다르게 처리하면(대소문자·공백 등) 파일명이 어긋나 "스냅샷 없음"으로 잘못 판정된다. 형식/정규화 규칙이 정해지면 두 명령에 **똑같이** 적용해야 한다.

## 2단계: 이슈-브랜치 정합성 확인
- 현재 git 브랜치명을 확인해줘.
- 브랜치명이 대상 키와 다르면(= `jira-start`가 만드는 브랜치명 규칙 기준으로 불일치), 다른 이슈 작업 중 실수로 동기화하는 상황일 수 있으니 사용자에게 알리고 계속 진행할지 확인해줘 (임의로 브랜치를 전환하거나 계속 진행하지 마).
  - 비교 기준은 `jira-start`의 브랜치명 규칙과 동일해야 한다. (현재는 브랜치명 = 키. 팀이 접두어 컨벤션(예: `feature/<KEY>`)을 도입하면 이 비교 기준도 함께 맞춰야 한다.)

## 3단계: 기존 Jira 정보 로드 (기준선)
- `.claude/jira-snapshots/<KEY>.md` 파일을 읽어줘.
- 파일이 없거나, 내용이 비었거나 손상돼 비교 기준으로 쓸 수 없으면:
  - 비교 기준이 되는 스냅샷이 없다는 것을 사용자에게 알리고, 먼저 `/jira-start <KEY>`를 실행해 스냅샷을 생성하도록 안내한 뒤 종료해줘. (이 경우 4단계 이후는 진행하지 않는다.)

## 4단계: 현재 Jira 정보 조회
- 연결된 Atlassian(Jira) MCP로 대상 이슈의 현재 정보를 조회해줘.
- **이슈를 가져오지 못하면(MCP 미연결 / 존재하지 않는 키 / 권한 없음 등) 여기서 중단하고 원인을 보고해줘.**
  현재 정보가 비면 이후 3-way 비교에서 모든 항목이 삭제/변경된 것처럼 잘못 나오므로, 비교 단계로 넘어가지 않는다.
- 확인 항목:
  - Parent Story (목적 / 요구사항)
  - 현재 이슈 제목 / 설명 / 작업 범위
  - Acceptance Criteria
  - 일정(Start / Due) / Dependency(Blocks / Is blocked by)
  - 상태(Status)
  - Jira 최종 수정 시각(updated 필드)

## 5단계: 현재 Source Code 확인
- 이 이슈와 관련된 파일 / 모듈을 찾아, 현재 구현이 "기존 Jira 정보(스냅샷)" 기준 요구사항을 어떻게 충족하고 있는지 파악해줘.

## 6단계: 3-way 비교 및 변경 영향 분석
- **빠른 1차 확인**: 스냅샷의 Jira `updated` 시각과 현재 `updated` 시각을 먼저 비교한다. 동일하면 실질 변경이 없을 가능성이 크다(그래도 아래 항목 비교로 교차 확인).
- 아래 세 가지를 비교해 표나 목록으로 정리해줘.
  - 기존 Jira 정보 (스냅샷)
  - 현재 Jira 정보 (실시간 조회)
  - 현재 Source Code (실제 구현 상태)
- 정리할 내용:
  - **변경된 항목**: 설명, AC, 일정, Dependency, 범위 등에서 무엇이 바뀌었는지
  - **변경 영향**: 기존 구현 중 더 이상 요구사항과 맞지 않거나 수정이 필요한 부분
  - **추가 구현 범위**: 새로 생긴 요구사항 중 아직 코드에 반영되지 않은 부분
- **변경 사항이 없으면**: "변경 사항 없음"이라고 명확히 알리고 여기서 종료한다. (7·8단계는 진행하지 않는다.)

## 7단계: 승인 대기  (변경이 있을 때만)
- 변경 영향과 추가 구현 범위를 사용자에게 보여주고, 진행 여부를 물어봐.
- 사용자가 명시적으로 승인하기 전까지는 코드를 수정하지 마.

## 8단계: 구현 및 스냅샷 갱신  (승인 후)
- 사용자가 승인하면, 확인된 변경 영향·추가 구현 범위에 따라 구현을 진행한다.
- **스냅샷 갱신은 승인한 변경을 코드에 반영 완료한 뒤에만** `.claude/jira-snapshots/<KEY>.md`에 수행한다.
  - 이유: 스냅샷은 "현재 코드가 반영하고 있는 Jira 상태"를 의미한다. 구현 전에 갱신하면 코드는 옛 요구사항인데 기준선만 새 요구사항으로 앞서가, 다음 `/jira-sync`에서 미구현분이 "변경 없음"으로 가려진다.
  - 저장 형식은 `jira-start`가 저장한 것과 **동일한 스키마**로 한다 (저장 시각, Jira updated, 이슈 키/제목/설명, AC, 일정, Dependency, Parent Story를 원문 그대로). 형식이 달라지면 이후 diff 비교가 깨진다.

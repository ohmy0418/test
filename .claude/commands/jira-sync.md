너는 개발자가 Jira 요구사항 변경을 안전하게 반영하도록 돕는 개발 어시스턴트야.
대상 이슈: $ARGUMENTS

**중요 원칙: 요구사항이 변경된 것을 발견하더라도 코드를 임의로 수정하지 마. 분석 결과를 먼저 보여주고, 개발자가 명시적으로 진행을 승인한 뒤에만 구현을 시작해.**

## 0단계: 이슈-브랜치 정합성 확인
- 현재 git 브랜치명을 확인해줘.
- 브랜치명이 `$ARGUMENTS`와 다르면, 다른 이슈 작업 중 실수로 동기화하는 상황일 수 있으니 이를 사용자에게 알리고 계속 진행할지 확인해줘 (임의로 브랜치를 전환하거나 계속 진행하지 마).

## 1단계: 기존 Jira 정보 로드
- `.claude/jira-snapshots/$ARGUMENTS.md` 파일을 읽어줘.
- 파일이 없으면: 비교 기준이 되는 스냅샷이 없다는 것을 사용자에게 알리고, 먼저 `/jira-start $ARGUMENTS`를 실행해 스냅샷을 생성하도록 안내한 뒤 종료해줘. (이 경우 2단계 이후는 진행하지 않음)

## 2단계: 현재 Jira 정보 조회
연결된 Atlassian(Jira) MCP로 `$ARGUMENTS` 이슈의 현재 정보를 조회해줘.
- Parent Story (목적/요구사항, 변경 여부 포함)
- 현재 이슈 제목/설명/작업 범위
- Acceptance Criteria
- 일정(Start/Due) / Dependency(Blocks / Is blocked by)
- 상태(Status)

## 3단계: 현재 Source Code 확인
- 이 이슈와 관련된 파일/모듈을 찾아 현재 구현이 "기존 Jira 정보(스냅샷)" 기준 요구사항을 어떻게 충족하고 있는지 파악해줘.

## 4단계: 3-way 비교 및 변경 영향 분석
아래 세 가지를 비교해서 표나 목록으로 정리해줘.
- 기존 Jira 정보 (스냅샷)
- 현재 Jira 정보 (실시간 조회)
- 현재 Source Code (실제 구현 상태)

정리할 내용:
- **변경된 항목**: 설명, AC, 일정, Dependency, 범위 등에서 무엇이 바뀌었는지
- **변경 영향**: 기존 구현 중 더 이상 요구사항과 맞지 않거나 수정이 필요한 부분
- **추가 구현 범위**: 새로 생긴 요구사항 중 아직 코드에 반영되지 않은 부분
- 변경이 없다면 "변경 사항 없음"이라고 명확히 알려줘.

## 5단계: 승인 대기
- 변경 영향과 추가 구현 범위를 사용자에게 보여주고, 진행 여부를 물어봐.
- 사용자가 명시적으로 승인하기 전까지는 코드를 수정하지 마.

## 6단계: 스냅샷 갱신 (승인 후 진행 시)
- 사용자가 승인해서 구현을 진행하기로 하면, 구현 전이든 후든 `.claude/jira-snapshots/$ARGUMENTS.md`를 현재 Jira 정보로 갱신해서 다음 `/jira-sync` 비교 기준점을 최신화해줘.

너는 개발자가 작업을 시작하도록 돕는 개발 어시스턴트야.
아래 Jira 이슈를 기준으로 개발 준비 상태를 확인하고 구현 계획을 세워줘.
각 단계는 순서대로 진행하고, 실행한 명령과 그 결과를 사용자에게 보여줘.

대상 이슈: $ARGUMENTS

## 1단계: 입력값 검증
- `$ARGUMENTS`가 비어 있으면 중단하고, 이슈 키를 입력하라고 안내해줘.
- 이슈 키 형식은 아직 확정되지 않았으니 특정 형식을 강제하지 않는다. 입력받은 값을 그대로 이슈 키로 사용한다.
  - 다만 공백으로 여러 값이 들어오면(예: `GAF-11 급함`) 어느 것이 이슈 키인지 모호하므로, 임의로 추측하지 말고 중단해서 사용자에게 확인해줘.
- 앞뒤 공백만 제거하고, 값 자체는 사용자가 입력한 그대로 Jira 조회·브랜치명에 사용한다. (형식이 정해지면 그때 정규화 규칙을 추가한다.)

## 2단계: Jira 정보 확인
- 연결된 Atlassian(Jira) MCP로 대상 이슈를 조회해줘.
- **이슈를 가져오지 못하면(MCP 미연결 / 존재하지 않는 키 / 권한 없음 등) 여기서 중단하고 원인을 보고해줘.**
  빈 데이터로 다음 단계(스냅샷 저장·브랜치 생성)로 절대 넘어가지 않는다.
- 다음을 확인한다.
  - 현재 이슈(Sub-task): 제목 / 설명 / 작업 범위
  - Parent Story: 상위 Story를 **추가로 조회**해 목적 / 요구사항 확인
  - Acceptance Criteria (완료 조건)
  - 일정: Start / Due
  - Dependency: Blocks / Is blocked by
  - Jira 최종 수정 시각(updated 필드) — 스냅샷 기준용
- **Blocked 판정**: 이 이슈가 미해결 이슈에 의해 blocked 상태라면, 그 사실을 눈에 띄게 표시해줘 (4단계에서 진행 여부를 확인한다).

## 3단계: 스냅샷 저장 (변경 감지 기준선)
> 이 단계는 계획을 보여주기 전에 반드시 수행한다. `/jira-sync`가 비교할 기준선이므로 누락되면 안 된다.

스냅샷은 **두 개의 파일**로 저장한다. 디렉터리가 없으면 `mkdir -p .claude/jira-snapshots`로 먼저 생성해줘.

| 파일 | 용도 |
|---|---|
| `.claude/jira-snapshots/<KEY>.json` | **기계 비교용 기준선.** `/jira-sync`의 1차 판정이 이 파일의 `diff` 결과를 근거로 한다. |
| `.claude/jira-snapshots/<KEY>.md` | 사람이 읽는 요약. 판단 근거가 아니라 참고용이다. |

- **이미 스냅샷 파일이 있으면 덮어쓰지 않는다.**
  - 기존 파일은 "이 작업을 처음 시작할 때 본 Jira 상태"라는 기준선이다. 재작업(이어서 작업) 시 이 기준선을 보존해야 `/jira-sync`가 그 사이의 변경을 감지할 수 있다.
  - 파일이 있으면 "기존 스냅샷 유지 (기준선 보존)"라고 사용자에게 알려줘.
  - `.md`만 있고 `.json`이 없는 이슈(JSON 도입 이전에 만들어진 스냅샷)라면, **`.json`만 지금 시점 값으로 새로 만들지 않는다.** 그 사이의 변경이 기준선에 흡수되어 영원히 감지되지 않기 때문이다. "이 이슈는 JSON 기준선이 없어 `/jira-sync`가 md 기준 비교로만 동작한다"고 사용자에게 알린다.
  - (기준선을 의도적으로 새로 잡아야 한다면, 사용자가 해당 파일들을 직접 삭제한 뒤 다시 실행한다.)

### 3-1. JSON 스냅샷 (`<KEY>.json`)

Jira 응답 값을 **재서술·요약·번역하지 말고 원문 문자열 그대로** 담는다. 이 파일은 텍스트 diff의 대상이므로, 한 글자라도 모델이 다듬으면 다음 `/jira-sync`에서 거짓 변경으로 잡힌다. 값이 없는 필드는 임의로 채우지 말고 `null`로 둔다.

필드 구성은 아래 스키마를 그대로 지킨다. 필드를 빼거나 임의로 추가하면 diff에 거짓 변경으로 잡힌다 (키 순서는 비교 시점에 정규화되므로 상관없다).

```json
{
  "key": "GAF-49",
  "capturedAt": "2026-08-31T14:02:11+09:00",
  "updated": "2026-08-31T08:20:47.675+0900",
  "status": "해야 할 일",
  "issueType": "Sub-task",
  "summary": "<원문>",
  "description": "<원문 그대로. 개행은 \n으로 이스케이프>",
  "acceptanceCriteria": "<원문 그대로. 별도 필드가 없으면 description에서 AC 부분만 원문 그대로 발췌>",
  "startDate": "2026-08-31",
  "dueDate": "2026-09-15",
  "assignee": "오민영",
  "sprint": null,
  "dependencies": {
    "blocks": ["GAF-50"],
    "isBlockedBy": []
  },
  "parent": {
    "key": "GAF-43",
    "updated": "<Parent Story의 updated 원문>",
    "summary": "<원문>",
    "description": "<원문 그대로>"
  }
}
```

- `parent.updated`를 반드시 포함한다. **Story 변경 감지가 이 필드 하나에 달려 있다.** Sub-task 스냅샷이 Parent의 최종 수정 시각을 함께 들고 있어야, Story 요구사항이 바뀐 것을 별도의 Story 스냅샷 없이 `/jira-sync`에서 잡을 수 있다.
- Parent가 없는 이슈(Story/Task 등)면 `"parent": null`로 둔다.
- 저장 후 `python3 -m json.tool <KEY>.json > /dev/null`로 파싱 가능한지 확인하고, 실패하면 사용자에게 알린다. 깨진 JSON은 기준선 역할을 못 한다.

### 3-2. 마크다운 스냅샷 (`<KEY>.md`)

사람이 훑어보기 위한 요약이다. 다음을 담는다: 조회 시각(날짜+시각), Jira updated, Web URL, 기본 정보(타입/요약/상태/담당자/일정/Sprint), Parent Story의 목적·요구사항·AC, 현재 이슈의 작업 내용·완료 조건, Dependency.

## 4단계: 작업 브랜치 준비
- 먼저 `git status`로 현재 uncommitted 변경사항이 있는지 확인해줘.
  - 현재 브랜치가 대상 키가 아니고 uncommitted 변경이 남아 있다면(= 다른 이슈 작업 중이던 변경), **임의로 버리지 말고** 사용자에게 알려서 커밋할지·stash 할지 확인해줘. 확인 전에는 브랜치를 전환하지 않는다.
- 2단계에서 이 이슈가 **blocked**로 확인됐다면, 브랜치를 만들기 전에 "미해결 선행 작업(Is blocked by)이 있다"고 경고하고, 그래도 시작할지 사용자에게 확인해줘.
- 브랜치 처리 (브랜치명 = 대상 키):
  - 로컬에 `<KEY>` 브랜치가 이미 있으면 `git checkout <KEY>`로 전환만 한다 (재작업 / 이어서 작업).
  - 없으면 **최신 기본 브랜치에서** 새로 생성한다:
    ```
    git checkout main
    git pull
    git checkout -b <KEY>
    ```
    - 기본 브랜치는 현재 `main` 기준이다. (팀 기준 확인 후 확정 필요 — 다르면 이 값을 조정한다.)
- 브랜치 생성/전환은 로컬 작업이므로 별도 승인 없이 진행하되, 실행한 git 명령과 결과를 사용자에게 보여줘.
- 이후 모든 구현 작업은 이 브랜치에서 진행한다.

## 5단계: 코드베이스 확인
- 현재 Repository 구조를 파악하고, 이 작업과 관련된 파일 / 모듈을 찾아줘.

## 6단계: 구현 계획 수립
- 구현 범위를 정리한다.
- Acceptance Criteria를 만족시키기 위한 단계별 구현 계획을 제시한다.
- **준비 상태(READY/AT RISK/NOT READY) 판정은 `dev-readiness` 서브에이전트를 호출해 받아온 결과를 그대로 사용한다.** 이 커맨드에서 별도의 판정 로직을 다시 만들지 않는다 (판단 기준이 두 곳에서 따로 관리되면 서로 어긋날 수 있다).
- **아직 코드는 작성하지 않는다.** 아래 형식으로 정리해 보여주고 사용자의 확인을 기다린다. 사용자가 진행을 승인하면 7단계로 넘어간다.

### 최종 출력 형식
1. **Jira 요약**: 이슈 키 / 제목, Parent Story, Acceptance Criteria, 일정
2. **준비 상태**: `dev-readiness` 서브에이전트의 판정(READY / AT RISK / NOT READY) 및 근거  (+ 블로커가 있으면 명시)
3. **브랜치**: 사용 중인 브랜치명, 신규 생성 / 기존 전환 여부
4. **구현 계획**: 단계별 목록
5. **확인 필요 사항**: 부족하거나 모호해서 사용자 확인이 필요한 항목
## 7단계: 구현 착수 승인 및 Jira 상태 전이

사용자가 6단계의 계획을 확인하고 **구현 진행을 승인하면**, 구현을 시작하기 전에 Jira 상태를 진행 중으로 전이한다.

- 전이는 `jira-status-updater` 서브에이전트에게 위임한다. 이 커맨드에서 `transitionJiraIssue`를 직접 호출하지 않는다.
- **별도의 승인을 다시 받지 않는다.** 6단계의 "구현 진행 승인"이 곧 착수 선언이며, 상태 전이는 그 승인에 포함된 동작이다. 승인 트리거를 늘리지 않기 위한 의도적인 설계다.
- 다음 경우에는 전이하지 않는다.
  - 준비 상태가 `NOT READY`인 경우 (착수 자체가 보류 상태다)
  - 이미 진행 중 계열 상태인 경우 (재작업으로 `/jira-start`를 다시 실행한 상황)
  - 사용 가능한 전이 중 어느 것이 "진행 중"인지 모호한 경우 → 전이하지 않고 후보를 보여준 뒤 사용자에게 선택을 요청한다
- 전이에 실패해도(권한 부족, 워크플로 제약 등) **구현 진행은 막지 않는다.** 실패 사실만 알리고 계속 진행한다. 상태 전이는 기록용이지 개발의 선행 조건이 아니다.
- 전이 결과(이전 상태 → 현재 상태, 또는 건너뛴 사유)를 사용자에게 한 줄로 보고한다.

구현이 끝나 커밋·PR까지 마쳤다면 `/jira-done <KEY>`로 완료 처리를 이어간다.
